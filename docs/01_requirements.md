# 01. システム要件定義書

## 1. ドキュメントの目的

本ドキュメントは「SNS AIバズ分析プラットフォーム」（以下「本システム」）の要件を定義するものです。本システムに関わるすべてのメンバー（企画・開発・QA・運用）が同じ前提を共有できるよう、背景・目的・スコープ・非機能要件・制約事項を明文化します。

以降のドキュメント（`02_features.md` 以降）は、本ドキュメントで定義した用語・スコープ・制約を前提として作成されています。用語の表記は全ドキュメントで統一します（詳細は「4. 用語定義」を参照）。

## 2. 背景

- Instagram / TikTok / X（旧Twitter）をはじめとする SNS 上では、日々膨大な数の投稿が公開されており、その中から「バズった」投稿には共通の要因（フック、構成、投稿時間、ハッシュタグの使い方など）が存在すると考えられる。
- 個人クリエイターや企業のSNS担当者は、こうした要因を経験と勘に頼って分析しており、再現性のある改善サイクルを回すことが難しい。
- 一方で、SNS各社は自社プラットフォームの非公開データ（インプレッション、リーチ、保存数、フォロワーのデモグラフィックなど）をAPIで第三者に開放していないケースが多く、非公式なスクレイピングは利用規約違反・アカウント凍結・法的リスクを伴う。
- そこで、**公式APIで取得可能な公開データのみ**を用いて、AI（LLM）による定性・定量分析を組み合わせ、「なぜバズったか」「次に何を投稿すべきか」を提案するプラットフォームのニーズがある。

## 3. 目的

1. Instagram / TikTok / X の**公開投稿**のデータを、各社が提供する公式APIを通じて適法に取得する。
2. 取得したデータをもとに、AI（OpenAI API）が投稿の「バズった理由」「ターゲット層」「フック」「CTA」「感情」「構成」などを分析し、独自指標「BuzzScore（0〜100点）」を算出する。
3. 自アカウント・競合アカウントの投稿を横断的に比較し、伸びる投稿の傾向やジャンル・投稿時間・投稿頻度などの知見を提供する。
4. 分析結果をワンクリックで PDF / Markdown / HTML のレポートとして出力し、社内共有やクライアント報告に利用できるようにする。
5. 将来的に YouTube / Pinterest / Threads など対応SNSを追加できる拡張性の高いアーキテクチャを採用する。

## 4. スコープ

### 4.1 対象範囲（In Scope）

- Instagram / TikTok / X の**公開アカウントの公開投稿**データの取得・保存・分析
- 投稿URLを入力した単体投稿分析（AI分析、BuzzScore算出、改善提案、類似投稿提案）
- キーワード検索・ハッシュタグ検索・アカウント検索
- 競合アカウント分析（アカウント単位の集計統計、伸びる投稿ランキング）
- トレンド分析・急上昇/週間/月間/ジャンル別/SNS別ランキング
- AIレポートの生成・保存・PDF/Markdown/HTML出力
- 分析結果の保存（保存済み分析）
- ユーザー認証（JWTベース）、ユーザー設定
- Web ダッシュボード（Next.js / React / TypeScript）

### 4.2 対象外（Out of Scope）

- 各SNSの**非公開データ**（インプレッション、リーチ、保存数、プロフィール閲覧数、フォロワーの属性情報、DM、非公開アカウントの投稿等）の取得
- 非公式API・スクレイピングによるデータ取得（利用規約違反となるため恒久的に禁止）
- SNSアカウントへの自動投稿・自動コメント・自動フォローなどの操作機能（分析・閲覧のみを対象とし、投稿代行は行わない）
- 個人を特定するようなプロファイリングや第三者の非公開情報の収集
- 本リリースにおける YouTube / Pinterest / Threads 対応（将来拡張として設計上のみ考慮する。詳細は `07_class_diagram.md` を参照）

## 5. 前提条件・制約事項（利用規約遵守 / API制約）

本システムの設計・実装における最重要の前提は以下の通りです。全機能はこれらの制約を満たす範囲でのみ実現します。

| # | 制約 | 内容 |
|---|------|------|
| C-1 | 公式API優先の原則 | データ取得は必ず各SNSが提供する公式API（Instagram Graph API / TikTok for Developers API / X API v2 など）を利用する。スクレイピングやHTML解析による非公式取得は行わない。 |
| C-2 | 公開データのみ取得 | 取得対象は「公開されている投稿・公開されているアカウント情報」に限定する。非公開アカウント、非公開投稿、フォロワー限定公開の情報は取得しない。 |
| C-3 | 取得項目の限定 | 取得するデータは以下に限定する：投稿URL、投稿ID、投稿日時、投稿者（アカウント）情報、キャプション、ハッシュタグ、いいね数、コメント数、再生数（公開されている場合）、シェア数（取得可能な場合）、動画時間、画像枚数、公開メタデータ、投稿種別（リール/画像/動画/カルーセル/テキスト）。インプレッション・リーチ・保存数など非公開データは対象外。 |
| C-4 | APIレート制限順守 | 各プラットフォームAPIのレート制限（Rate Limit）を遵守し、指数バックオフ・キューイングによる制御を行う。制限超過による強制停止を回避する設計とする。 |
| C-5 | APIポリシー変更への追従 | 各SNSの開発者ポリシー・APIの仕様変更に迅速に追従できるよう、SNS連携部分は `SocialPlatform` 抽象インターフェースの背後に隠蔽し、影響範囲をプラットフォーム実装クラス内に閉じ込める（詳細は `07_class_diagram.md`）。 |
| C-6 | データ保持・削除 | 各SNSの利用規約が定めるデータ保持期間・削除要求（投稿削除時の追従等）に対応できるよう、定期的な再取得・整合性チェックの仕組みを設ける。 |
| C-7 | クレジット表記・帰属 | 表示・レポート上で、投稿の出典（投稿者アカウント、投稿URL、SNS名）を明示し、一次情報への帰属を保つ。 |
| C-8 | 自動化された投稿・エンゲージメント操作の禁止 | 本システムは分析・提案のみを行い、SNSアカウントへの自動投稿・自動いいね・自動フォロー等は一切行わない。 |

## 6. 用語定義

全ドキュメント共通で以下の用語・表記を使用します。

| 用語 | 定義 |
|------|------|
| プラットフォーム（Platform） | Instagram、TikTok、X などのSNSサービスそのもの。DB上は `platforms` テーブルで管理。 |
| SNSアカウント（Social Account） | 分析対象となるSNS上の公開アカウント（自社アカウント・競合アカウントを含む）。DB上は `social_accounts` テーブル。 |
| 投稿（Post） | SNSアカウントが公開した1件の投稿（リール/画像/動画/カルーセル/テキスト）。DB上は `posts` テーブル。 |
| 投稿種別（Post Type） | `REEL`（リール）/ `IMAGE`（画像）/ `VIDEO`（動画）/ `CAROUSEL`（カルーセル）/ `TEXT`（テキスト）の5種類。 |
| 投稿メトリクス（Post Metrics） | いいね数・コメント数・再生数・シェア数など、時点ごとに変化する公開数値。DB上は `post_metrics` テーブル（時系列スナップショット）。 |
| AI分析結果（Analysis Result） | AIが投稿を解析した結果一式（バズ理由、ターゲット層、フック、CTA、感情分析等）。DB上は `analysis_results` テーブル。 |
| BuzzScore | 投稿の「伸び具合・完成度」を0〜100点で表す独自指標。複数のスコアリング戦略（Strategyパターン）を合成して算出。DB上は `buzz_scores` テーブル。 |
| 競合統計（Competitor Stats） | SNSアカウント単位で集計した平均いいね数・平均コメント数・投稿頻度などの統計値。DB上は `competitor_stats` テーブル。 |
| レポート（Report） | AI分析結果をPDF/Markdown/HTMLに変換した出力物。DB上は `reports` テーブル。 |
| ランキング（Ranking） | 急上昇/週間/月間/ジャンル別/SNS別に投稿を順位付けした一覧。DB上は `rankings` / `ranking_entries` テーブル。 |
| 保存済み分析（Saved Analysis） | ユーザーがブックマークした分析結果。DB上は `saved_analyses` テーブル。 |
| ハッシュタグ（Hashtag） | 投稿に付与されたタグ文字列。DB上は `hashtags` / `post_hashtags` テーブル。 |

## 7. 非機能要件

### 7.1 性能（パフォーマンス）

| 項目 | 要件 |
|------|------|
| API応答時間 | 一覧・検索系APIは95パーセンタイルで500ms以内（キャッシュヒット時）。AI分析・BuzzScore算出を伴う投稿URL分析APIは非同期ジョブ化し、同期レスポンスは受付完了（202 Accepted）を1秒以内に返す。 |
| 同時実行 | 初期リリースで同時アクティブユーザー数500、ピーク時のAPIリクエスト100 req/sを想定したスケーリング設計とする。 |
| バッチ処理 | ランキング再計算・競合統計再集計などのバッチは深夜帯に実行し、1バッチあたり30分以内に完了させる。 |
| キャッシュ戦略 | Redisを用いて、ランキング・トレンド・競合統計などの読み取り頻度が高いデータをキャッシュし、DB負荷を軽減する（TTLはデータ種別ごとに設定）。 |

### 7.2 セキュリティ

| 項目 | 要件 |
|------|------|
| 認証 | JWT（アクセストークン + リフレッシュトークン）による認証。アクセストークンは短寿命（例: 15分）、リフレッシュトークンは長寿命かつ失効管理を行う。 |
| 認可 | ロールベースアクセス制御（RBAC）。`USER` / `ADMIN` ロールを基本とし、将来のプラン別機能制限（FREE/PRO/ENTERPRISE）にも対応できる設計とする。 |
| 通信 | すべての通信をTLS1.2以上で暗号化する。 |
| 秘匿情報管理 | 各SNS公式APIのAPIキー・アクセストークン、OpenAI APIキーなどはシークレットマネージャ（例: AWS Secrets Manager 等、初期はDocker Secrets/環境変数）で管理し、リポジトリに含めない。 |
| 入力バリデーション | 投稿URL入力、検索キーワード等はサーバーサイドでバリデーション・サニタイズし、SQLインジェクション・XSS・SSRFを防止する（特にURL分析機能はSSRF対策が必須）。 |
| 監査ログ | ユーザーの重要操作（ログイン、レポート出力、設定変更、アカウント登録）を監査ログとして記録する。 |
| 依存脆弱性管理 | Gradle依存関係・npmパッケージの脆弱性を定期スキャンする。 |

### 7.3 可用性

| 項目 | 要件 |
|------|------|
| 稼働率目標 | 月間稼働率99.5%以上（初期リリース時点、Docker Compose単一環境を想定。将来のクラウド移行後は99.9%を目指す）。 |
| 障害時の縮退運転 | 外部SNS APIやOpenAI APIが一時的に利用不可でも、既存の分析結果・ランキング等の閲覧機能は継続提供する（新規分析のみ受付停止）。 |
| バックアップ | PostgreSQLは日次フルバックアップ + WALによるポイントインタイムリカバリを行う。 |
| ヘルスチェック | 各サービス（backend/frontend/DB/Redis/Storage）にヘルスチェックエンドポイントを実装し、コンテナオーケストレーションから監視できるようにする。 |

### 7.4 拡張性・保守性

| 項目 | 要件 |
|------|------|
| SNS追加の容易性 | 新規SNS（YouTube/Pinterest/Threads等）追加時、`SocialPlatform` インターフェースを実装するクラスを1つ追加し、`PlatformFactory` に登録するだけで既存機能（検索・分析・ランキング等）に組み込めること。既存コードの大規模な改修を必要としない。 |
| BuzzScoreロジックの拡張性 | 新たな採点基準を追加する場合、`BuzzScoreStrategy` を1つ追加するだけで合成ロジックに組み込めること（Strategyパターン）。 |
| レイヤー分離 | クリーンアーキテクチャに基づき、ドメイン層が外部フレームワーク・DB・外部APIに依存しないこと（依存性逆転の原則）。 |
| テスト容易性 | ドメイン層・アプリケーション層は外部依存をインターフェース経由でモック化し、単体テストカバレッジ80%以上を目標とする。 |
| インフラ可搬性 | 初期はDocker Composeで単一ホスト上に構築するが、将来的にAWS ECS/Cloud Run/Kubernetesへ移行可能なよう、12-factor app原則（設定の外部化、ステートレス化）に従う。 |

### 7.5 運用・監視

| 項目 | 要件 |
|------|------|
| ロギング | 構造化ログ（JSON形式）を出力し、リクエストID・ユーザーIDをトレースできるようにする。 |
| メトリクス監視 | APIレイテンシ・エラー率・外部API呼び出し成功率・OpenAI APIコストなどを可視化する。 |
| アラート | 外部API連携失敗率が閾値を超えた場合、AI分析ジョブが一定時間以上滞留した場合にアラートを発報する。 |
| コスト管理 | OpenAI API利用量・各SNS API呼び出し回数をユーザー/プラン単位で計測し、コスト超過を防止する仕組みを設ける。 |

## 8. ステークホルダー

| ステークホルダー | 関心事 |
|------------------|--------|
| SNS運用担当者・クリエイター（エンドユーザー） | 自分の投稿・競合投稿の分析結果を素早く得て、次の投稿改善に活かしたい |
| マーケティング会社・代理店 | クライアント向けレポートをワンクリックで出力したい |
| プロダクトオーナー | 利用規約違反リスクを避けつつ、SNS追加を柔軟に行いたい |
| 開発チーム | クリーンアーキテクチャに基づき保守性・テスト容易性の高いコードベースを維持したい |
| 運用チーム | 外部API制限・コストを監視し、安定運用したい |

## 9. リスクと対応方針

| リスク | 影響 | 対応方針 |
|--------|------|----------|
| SNS公式APIの仕様変更・提供終了 | 特定SNSのデータ取得が停止する | `SocialPlatform` 抽象化により影響を1実装クラスに局所化。複数SNS対応により単一障害点を回避。 |
| APIレート制限による取得遅延 | 分析結果の即時性が低下する | 非同期ジョブキュー化、キャッシュ活用、優先度制御。 |
| OpenAI API のコスト増大 | 運用コスト超過 | プロンプト最適化、分析結果キャッシュ、ユーザー/プランごとの利用上限設定。 |
| 非公開データ取得への圧力（ユーザー要望） | 規約違反リスク | 要件として非公開データは恒久的に対象外とすることをプロダクト方針として明文化（本書 5章）。 |
| 投稿削除・非公開化 | 保存済みデータと実際の投稿状態の乖離 | 定期的な再取得・存在確認バッチにより整合性を保つ。 |
